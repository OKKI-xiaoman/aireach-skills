## 0. 初始化

本技能依赖 OKKI AiReach 能力，执行前必须先确认 `aireach-cli` 可用且当前环境已授权。若缺少 `aireach-cli`，请先通过 npm 安装：`npm install -g @okki-aireach/aireach-cli`（或由宿主按插件约定注入），不要尝试绕过 CLI 直接调用内部接口。

执行前运行 `aireach-cli auth status` 检查登录状态，确认本地凭证与目标 gateway 环境匹配。若未登录或凭证失效，先按 `okki-aireach-auth-init` 的流程引导用户完成授权（授权 URL 需包含 `client_id=accio-work`），授权成功后再继续本技能任务。

不要要求用户粘贴或展示 PAT/token，也不要把授权登录路径、内部地址写进回复；认证是否可用以目标 gateway 的真实请求验证结果为准，而不是只看本地是否有 token。
# AiReach Import and Export Query

## 能力边界
- 这是对 AiReach 现有贸易单据查询能力的封装，不额外假设新的贸易聚合能力。
- AiReach 通过运行时暴露的业务 capability 执行。对外语义统一视为 AiReach 产品能力，而不是让 agent 直接操作底层实现名。
- 重点是把公司名、HS 编码、产品词映射到稳定的贸易查询业务参数，并在 skill 层完成参数优化与结果整理。

## 适用场景
- 用户输入公司名，想看该公司相关的进出口记录、最近交易和常见货物线索。
- 用户输入 HS 编码，想快速查看相关采购商、供应商与近期交易记录。
- 用户输入产品词，想查海关/贸易单据并输出便于阅读的表格结果。
- 用户指定数据国家、进口商国家、出口商国家或时间范围，希望结构化检索贸易记录。
- 用户希望基于返回的海关样本做买家、供应商、竞品、品类、HS 或产品机会分析，并判断这些样本与当前卖家业务画像的匹配度。
- 用户想从产品、HS、竞品公司或买家公司出发找真实买家/采购商，并判断哪些买家值得开发，例如“帮我找美国采购庭院灯的买家有哪些”“查一下竞品 xxx 都卖给了哪些采购商”。
- 用户想从采购商国家、供应商国家、产品或 HS 出发找品类机会，并判断是否有市场、能不能做，例如“美国最近进口量高的园艺类产品有哪些”“这个 HS 在哪些国家需求比较大”“越南出口增长比较快、和我业务相关的品类有哪些”。

## 不适用场景
- 任务要求写操作、异步长任务、批量导出，或者超出当前贸易查询 capability 覆盖的查询范围。
- 任务要求把 client_id、shared secret、宿主绑定配置或内部部署地址写进 skill 包。
- 任务要求返回 MCP capability 或 CLI 执行面未提供的全量聚合指标；如果底层没有可信字段，不要编造总金额或全局统计。
- 任务要求完整市场趋势、全量统计、多页爬取、CSV 导出、定时推送、创建营销任务、状态回写、生成或更新卖家画像。


## 普通查询 vs 机会分析
- **普通贸易单查询**：只调用贸易查询 capability，返回记录摘要和样本表；不要强制读取卖家画像。
- **海关样本机会分析**：先读取当前租户已持久化的卖家画像，再按用户意图调用有边界的贸易查询 capability，并基于返回样本或工具返回的聚合数据做解释。
- 卖家画像只用于相关性、匹配度、"我们能不能做"等判断；不得把画像信息表述成海关事实。
- 卖家画像是只读上下文。若画像 `profile_status` 为 `missing` 或 `incomplete`，且缺失字段会影响判断，向用户追问具体业务背景；不得触发画像生成、更新或修复。

## 海关样本机会分析

分成两类：找真实买家和找品类机会。
两类都只能基于贸易查询 capability 返回的记录、total、sample_size 和可信聚合字段做判断；如果 capability 返回了交易总单据量、交易总额、国家分布、买家数、供应商数等聚合数据，直接使用这些聚合数据，不要再用返回样本估算统计。若底层只返回样本而没有可信聚合字段，必须写明“基于本次返回样本”；这些都是内部判断口径，不得编造，也不得把样本结论夸大为全量统计、完整趋势或全市场判断。

**客户可见输出原则**：机会分析的客户可见输出一律不展示 `total`、`sample_size`、最终查询参数（如 `keyword`、`search_type`、`importer_country_codes`）、样本口径、“基于本次返回样本 / 基于 X 条样本”等技术口径——这些只作内部判断依据，不要透传给客户

**数量上限（强约束）**：单次贸易查询最多返回约 100 条记录，没有全量数据。因此客户可见的任何数量——尤其是 `命中数量` 和导出条数——都不得超过本次实际返回的记录数（最多约 100）。`命中数量` 必须用本次返回样本去重后的采购商 / 品类数（必然 ≤ 返回记录数 ≤ 100），表述为“本次为您筛选出 xx 家采购商 / xx 个品类”。严禁把 `total` / `totalCompanyCount` 等总匹配数当作 `命中数量`，严禁出现500+、上千、上万这类超过实际返回量的数字，也不要写出 `sample_size` 数字。若内部 total 很大，只能在追问/筛选建议里说明“匹配范围较大，已为您聚焦本次返回的样本”，但不得把这个大数字写成命中数量或导出条数。

海关 MCP 工具按结果类型拆分：
- `trade_source_search` 用于贸易单据 / source record 查询。它返回的 `total` 表示匹配贸易单据数，不等于采购商或供应商公司数。
- `trade_company_search` 用于采购商 / 供应商公司结果查询。采购商数量、供应商数量、采购商列表、供应商列表必须优先调用这个工具；采购商用 `company_type=IMPORTER`，供应商用 `company_type=EXPORTER`，结果中的 `totalCompanyCount` 才是匹配公司数量，`totalRecordCount` 是匹配贸易单据数。

只有当最终询问对象明确是采购商 / 买家 / 供应商公司数量或公司列表时，才选择 `trade_company_search`。不要因为条件里出现“采购商是某国 / 供应商是某国”就自动选择 `trade_company_search`；这些词也可能只是单据筛选条件。如果最终询问对象是单据、记录、交易、进口信息、出口信息或它们的数量，仍然选择 `trade_source_search`。

工具选择必须先判断“采购商 / 供应商”在用户句子里的角色：
- 当“采购商是 X / 供应商是 Y”描述的是筛选条件，而用户问的是单据、记录、交易、进口信息或出口信息时，使用 `trade_source_search`。
- 当用户问“采购商有多少 / 买家有多少 / 供应商有多少”时，最终对象是商家，使用 `trade_company_search`。
- 例：`采购商是巴西、供应商是伊朗的交易记录有多少` → `trade_source_search`，因为要回答贸易单据数量。
- 例：`采购商是巴西、供应商是伊朗的采购商有多少` → `trade_company_search`，因为要回答采购商公司数量。
- 例：`HS 940542 近三个月的采购商有多少` → `trade_company_search`，`company_type=IMPORTER`，`search_type=HSCODE`，`hs_code=940542`，近三个月用工具 schema 支持的时间字段表达。

用户直接问“采购商有多少 / 买家有多少 / 供应商有多少”这类计数问题时，调用 `trade_company_search` 并从 `totalCompanyCount` 回答公司数量；这是显式计数问题，不同于机会分析概况里的 `命中数量`（命中数量按本次分析样本去重口径）。内部判断不要把 `trade_source_search.total`、`sample_size` 或样本内去重数误当作总采购商/供应商数量。

用户说“所有 / 全部买家”时，优先用 `trade_company_search` 返回的公司结果列表说明当前页公司样本和 `totalCompanyCount`；不得承诺已遍历所有页面。若只能拿到 `trade_source_search` 的分页单据样本，必须说明它不是全量公司结果，不得回答为全量买家数。

用户问“单据 / 记录 / 信息数量”时，用 `total` 回答匹配贸易单据数。记录数量回答不要只回复一个数字，要补一段业务摘要（最近交易时间、采购商/供应商、HS、金额、数量等）；不要向客户展示 `sample_size`、最终查询参数等技术口径。

### 找真实买家

- **基于产品 / HS / 竞品公司找买家**：适用于“DTF Printer 有哪些买家”“940350 主要采购商是谁”“竞品 xxx 卖给了哪些采购商”。产品和 HS 走产品/HS 查询；竞品公司走公司或 exporter 侧线索查询。默认查近一年活跃样本，优先看 importer 侧采购商，并把结果整理成推荐买家明细表。
- **基于买家公司下钻找竞品和更多买家**：适用于用户给出一个买家公司，想先看它从哪些供应商采购，再沿供应商线索寻找更多采购商。当前 P0 只能基于一次返回样本做供应商/采购商线索解释；如果需要真正的“供应商 -> 采购商”二跳全量分析，而当前 capability 未返回聚合或反查结果，要说明能力边界并建议用户选定供应商继续查询。
- 买家评估证据优先级：交易总单据量、交易总额、最近交易日期、近一年活跃、有联系人、只看有联系人、过滤物流公司、产品描述直接命中、进口趋势上升、供应商区域分布（尤其是否有中国或卖家所在地区供应商）。
- 如果 total 或可用聚合显示结果超过 100，内部最多分析 `size<=100` 的返回样本，客户侧只展示高优先级 Top 10（表述为“本次为您筛选出的高优先级 Top 10”，不暴露 size/sample_size），并建议按近一年/近半年、国家、金额、最近交易时间、有联系人、过滤物流公司继续收窄。
- 若用户直接问采购商数量，必须调用 `trade_company_search`，用 `company_type=IMPORTER`，并从 `totalCompanyCount` 回答。若同时提到单据数，只能把 `totalRecordCount` 解释为匹配贸易单据数。

### 找品类机会

- **基于采购商国家 / 地区找品类**：适用于“美国最近进口比较多、和我业务相关的品类有哪些”。查询该采购市场的进口数据，按 capability 返回的 HS、产品描述、金额、数量、频次、TOP 买家国家、TOP 供应商国家等字段整理品类机会。
- **基于供应商国家 / 地区找品类**：适用于“越南出口增长比较快、和我业务相关的品类有哪些”。查询该供应国的出口数据，按出口方向解释主流品类、流向国家和供应格局。
- **基于产品 / HS 找品类**：适用于“这个 HS 还有市场吗”“DTF Printer 机会主要在哪些国家”。从产品/HS 的进口数据看需求国家、采购商、供应商、交易频次、交易金额、数量和供应商结构。
- 品类评估证据优先级：交易总单据量、交易总额、最近 3 个月是否有交易、近 6/12 个月是否持续活跃、进口供应商增加、供应商区域分布、主要采购国家、主要供应国家、是否与卖家主营产品/行业/上下游/相邻品类匹配。
- 品类输出必须分清“主流趋势品类”和“与商家业务有关联的品类”。如果卖家画像不足以判断业务关联，先追问主营产品、目标市场、生产/贸易模式或供应能力。
- 不支持的品类起点：基于竞品公司找品类、基于买家公司找品类。遇到这类请求时说明本场景暂不支持公司反查品类，建议切到找真实买家，或改用采购商国家、供应商国家、产品或 HS 作为起点。

### 海关样本机会分析异常与追问

- 起点缺失：追问用户要基于产品、HS、买家公司、竞品公司、采购商国家还是供应商国家查询。
- 起点解析失败：追问用户给出的词是国家、产品名、HS 编码还是公司名。
- 产品词过宽：先说明可能需要更具体的产品词或 HS；若仍执行，只能做有限样本分析，并建议按国家、时间、HS 或产品关键词继续收窄。
- 公司名匹配多个主体：列出候选公司名称、国家、角色，让用户确认目标公司后再继续。
- 无结果：说明未找到匹配贸易记录，并建议扩大时间范围、切换进口/出口方向、放宽国家条件、改用 HS 或相邻产品词。
- 结果过多：若结果超过 100，客户侧展示高优先级 Top 10（不暴露 total/sample_size），并建议按金额、频次、近期活跃、国家、有联系人、业务匹配度继续筛选。
- 缺少金额、数量、联系人或物流公司识别字段：不得强行判断；用可用字段说明，并标记该结论置信度降低。

## 输入识别与映射
- **公司名**：放到 `company_keyword`，并把 `search_type` 设为 `COMPANY`。
- **HS 编码**：放到 `hs_code`，并把 `search_type` 设为 `HSCODE`。如果用户输入超过 6 位，先保留原值；当结果过少或无近一年数据时，退化为前 6 位再查。
- **产品词**：放到 `keyword`，并把 `search_type` 设为 `PRODUCT`。
- **国家条件**：
  - 只说“某国海关数据/贸易单” → `data_country_codes`
  - 明确说“进口商国家” → `importer_country_codes`
  - 明确说“出口商国家” → `exporter_country_codes`
- **方向条件**：未明确说明时默认优先补齐 `data_type=IMPDAT`；明确说出口再用 `EXPDAT`。
- **机会分析排序**：默认 `sort_field=DATE`、`sort_type=DESC`；用户明确要看金额/价值时用 `PRICE DESC`，看件数/数量时用 `PKG_NUM DESC`，看重量/体量时用 `WEIGHT DESC`。
- **机会分析样本量**：每次贸易查询都必须是 `page=1`，`size` 最大 100；不做多页采样，不为了扩大样本量重复同一查询。

## 参数优化规则
- **HS 截断**：当 HS 编码超过 6 位且结果过少、或缺少近一年数据时，退化到前 6 位重试一次。
- **公司名简化**：公司查询结果过少时，可按现有名称做最多两轮简化，例如去掉法律实体后缀、去掉尾部次要修饰词；每轮都必须保留明显的主体词，不要改成另一个公司。
- **产品词扩展**：当产品词结果过少时，可做有限的同义词或常见外文词扩展，但必须逐次执行、逐次判断，不要把国家、角色条件塞进 `keyword`。
- **稀疏判定**：当结果少于 10 条，或结果里没有近一年的记录时，可进入一次或两次有边界的退化重试。

## 使用要点
- 先把用户意图拆成结构化参数，再调用 MCP capability 或 CLI 执行面；不要把国家、角色或主体条件直接拼到 `keyword` 里。
- 不要默认把“公司名”塞到 `keyword`；公司查询优先使用 `company_keyword`。
- 国家代码统一使用 ISO 3166-1 alpha-2，例如 巴西=BR、美国=US、中国=CN。
- 如果用户是公司查询模式，优先返回 MCP capability 或 CLI 执行面真实支持的内容：总匹配量、最近记录、常见 HS/产品线索、样本交易明细。
- 如果用户是 HS/产品查询模式，优先返回去重后的近期采购商/供应商样本表。
- 如果底层结果没有可信的“总金额汇总”字段，就只返回真实可见的记录金额和样本摘要，不要伪造全局汇总。

## 执行流程

### 普通贸易单查询
1. 识别输入属于公司名、HS 编码、产品词或组合条件。
2. 生成第一版结构化参数：主体字段、国家字段、时间范围、方向、排序和分页。
3. 执行时按问题结果类型选择业务 capability：单据/记录/source record 用 `trade_source_search`；采购商/供应商公司数量或列表用 `trade_company_search`；具体通过宿主 capability 或 CLI 执行面调用由运行时可用性决定。
4. 获取首轮结果。
5. 如果命中稀疏：
   - HS 查询 → 按 6 位截断重试一次
   - 公司查询 → 做最多两轮公司名简化
   - 产品查询 → 做最多两轮有限词扩展
6. 选择命中最好、最近数据更合理的一次结果作为最终结果。
7. 输出时区分两种模式：
   - **公司模式**：返回公司相关的结果摘要 + 最近样本记录
   - **HS/产品模式**：返回去重后的近期交易表格
8. 明确返回最终采用的查询参数，以及是否发生过退化重试。

### 海关样本机会分析
1. 判断用户是否要求分析、评估、推荐、机会解读、匹配度判断，或问"哪些买家/供应商/品类更适合我们"。
2. 先读取卖家画像 capability，参数为 `include_site_page=true`；当前 AiReach MCP 工具名预期为 `client_profile_get`，但调用前仍以运行时 `tools/list` 返回的 schema 为准。必须等待 `client_profile_get` 调用完成并读取结果后，才能调用 `trade_source_search`；不要在同一轮工具调用里并行发起卖家画像和海关查询。
3. 卖家画像结果需要检查 `company_name`、`company_english_name`、`homepage` / `public_homepage`、`profile`、`products` / `primary_products`、`products_category` / `products_category_desc`、`type` / `company_type`、`company_industry`、`qualification`、`mode`、`product_page` / `site_page`，以及 `icp` / `icp_text`。其中 `icp` 是理想客户画像，来自 AiSdrSetting 的 `TYPE_ICP_FROM_DESC`，可用于目标客户匹配判断，但不要把它当作海关事实。
4. 如果画像缺少本次判断所需字段，先问用户一个有针对性的问题，例如主营产品、目标客户、生产/贸易模式、资质或 ICP；不要发起画像生成。
5. 生成贸易查询参数：保持国家、进口商/出口商、产品词、HS、时间范围等结构化字段分离。单据/记录查询默认 `DATE DESC`，`page=1`，`size<=100`，使用 `trade_source_search`；公司数量/列表查询默认 `sort=HIT_COUNT`，`page=1`，`size<=100`，使用 `trade_company_search`。
6. 单次贸易查询不翻页；不要多页爬取，不要用多种排序重复同一查询来扩大样本。若用户明确提出多个不同产品、国家、公司或 HS 起点，可以分别执行多个有边界的 `trade_source_search` 或 `trade_company_search`，但每次都必须 `page=1` 且 `size<=100`。
   - 默认不要给 `trade_source_search` 传 `include_company_status`。只有用户明确要求查看 CRM 建档、线索、浏览记录、公司状态等状态信息时，才传 `include_company_status=true`；海关样本机会分析默认不需要这类状态补充。
   - 不要在没有用户明确需求或确认的情况下主动调用 `company_contacts_fetch`、`contact_validity_check`、`company_background_check`、`potential_list_query` 或 `potential_list_export`；“哪些买家值得开发 / 优先关注”不是联系人获取、邮箱验证、公司背调或导出确认，这些通常只能作为 `下一步动作引导确认` 里的待用户确认动作。
   - 若用户当前请求已经明确要求背景核验、联系人获取、邮箱验证或已挖掘潜客导出，按对应 skill/工具契约执行，不要把“样本不翻页”误解成禁止其他工具。
7. 按意图选择分析对象：
   - 买家/客户问题：分析 importer 侧样本。
   - 供应商/竞品问题：分析 exporter 侧样本。
   - 品类/产品/HS 问题：分析 HS 与 product description 样本。
   - 模糊分析问题：输出买家、供应商、HS/产品的均衡样本概览。
8. 内部基于返回记录 / `total` / `sample_size` / 可信聚合字段做判断与排序；客户可见输出不展示这些技术口径，也不得把样本结论夸大为全市场或全周期统计。
9. 客户可见输出第一块是 `# 查询概况结果`，用 `#` 标题，下面逐项用 markdown 无序列表（`- 标签：值` 各占一行），按场景套用对应模板：

   找真实买家：

   ```
   # 查询概况结果
   - 查询链路：对应链路描述
   - 命中数量：xx 家采购商
   - 质量摘要：高推荐 xx 家、有中国供应商背景 xx 家
   ```

   找品类机会：

   ```
   # 查询概况结果
   - 查询链路：对应链路描述
   - 命中数量：xx 个品类
   - 质量摘要：高推荐 xx 个、与商家业务关联 xx 个
   ```
10. `查询概况结果` 里只放业务口径（查询链路 / 命中数量 / 质量摘要），不要出现 `total`、`sample_size`、最终查询参数、样本口径或“基于 X 条样本”。各概况项必须换行成独立列表项，不得与标题挤在同一段落。
11. 最终回答必须包含 `下一步动作引导确认` 业务块。
12. `下一步动作引导确认` 用自然、顺畅的第二人称口吻引导用户选下一步，控制在 2-3 条以内，每条是一个具体可点选的动作，不要堆砌工具名或术语。候选动作（按常用度取舍）：调整筛选（国家 / 时间 / 金额 / 有联系人 / 过滤物流公司等）；切换排序，或选定某个买家 / 品类继续下钻；导出完整明细列表（本次正文只展示了 Top 10，可导出本次返回的明细，最多约 100 条，需你确认；不要写成几百 / 全部条数）；经你确认后做公司背调、拉取联系人或验证邮箱；画像缺失背景时，补充后重跑判断。所有动作都先引导用户确认，不得在本次回答前主动执行。

## 约束
- 不得编造 `sourceId`、采购商、供应商、日期、金额、HS 编码或总量，只能引用真实返回值。
- 不得把国家、角色和主体条件退化成只拼接 `keyword`。
- 不要绕过 MCP capability / CLI 执行面契约去调用底层实现或额外包装脚本。
- 不得无限重试；每种输入最多做两轮有边界的退化优化。
- 不得把内部部署信息写入 skill 包。
- 机会分析不得把海关样本结论包装成全市场结论，不得承诺完整趋势、全量匹配数据导出或自动建营销任务；可在 `下一步动作引导确认` 里引导用户确认导出本次返回样本的完整明细（最多约 100 条），但不得承诺导出全量匹配数据或全市场数据。
- 单次查询最多返回约 100 条记录：客户可见的命中数量、导出条数等任何数量都不得超过本次实际返回量（≤100），严禁用 `total` / `totalCompanyCount` 等总匹配数充当命中数量，严禁出现 500+、上千、上万等超过返回量的数字。
- 机会分析中的推荐必须区分"海关样本事实"和"基于卖家画像/用户补充背景的判断"。
